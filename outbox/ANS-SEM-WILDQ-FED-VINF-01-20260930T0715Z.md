# 市场内核脉冲与 FINDING 落账节拍共振 — 可行性与首步

## 结论：可行，但需先解决一个结构性矛盾

**可行性判定：技术可行，治理上需先定权。**

市场异常检测是**高频率、低延迟**的脉冲流（毫秒到秒级），FINDING 落账是**有状态、需审计**的节拍流（秒到分钟级）。两者共振的本质不是“让 FINDING 追上脉冲”，而是**建立一个有损压缩但语义保真的降频管道**——异常脉冲必须先在缓冲层完成“聚合/去重/定级”，再触发 FINDING 生成。直接逐脉冲落账会导致公告板被噪声淹没，且审计不可用。

---

## 首步：定义“异常→FINDING”的触发契约

不要先写管道，先写**一张触发规则表**。这是整个直通管道的唯一语义入口：

| 维度 | 必须明确定义 |
|---|---|
| 异常类型 | 价格偏离、成交量突增、订单簿失衡、跨市场背离… |
| 脉冲阈值 | 统计基线 + 动态偏差（如 z-score > 3σ 持续 N 个 tick） |
| 聚合窗口 | 同一标的、同一类型在 T 窗口内合并为一个 FINDING |
| 定级规则 | P0/P1/P2 对应公告板的不同推送节拍 |
| 落账时机 | 窗口关闭时落账，而非脉冲到达时 |
| 幂等键 | `(标的, 异常类型, 窗口起始, 窗口结束)` |

**首步交付物**：这份触发契约 + 一个**回放验证**——用历史脉冲数据跑一遍，看生成的 FINDING 数量、定级分布、公告板噪声率是否可接受。如果 P2 级 FINDING 占比 > 80%，说明阈值或聚合窗口需要收紧，管道本身不用改。

---

## 直通管道的三段式架构（建议）

```
[市场脉冲源]
     │  (原始 tick / 异常事件)
     ▼
[共振缓冲层]  ← 核心：聚合、去重、定级、窗口管理
     │  (已定级的 FINDING 草案)
     ▼
[FINDING 落账器]  ← 有状态、幂等、可审计
     │  (正式 FINDING ID + 审计轨迹)
     ▼
[公告板分发]  ← 按定级走不同节拍（P0 即时 / P1 秒级 / P2 分钟级）
```

**关键设计点**：缓冲层是“有损”的——它主动丢弃低价值脉冲，只把满足触发契约的聚合结果往下游放。这不是缺陷，是共振的前提。没有这个有损层，脉冲和落账永远无法同频。

## 需要你确认的一个前置问题

**FINDING 落账的“节拍”目前是事件驱动还是定时批处理？**

- 如果是**事件驱动**：直通管道只需在缓冲层输出时调用落账接口，首步就是写触发契约 + 回放验证。
- 如果是**定时批处理**：需要先改造落账器支持“即时落账 + 批量对账”双模式，否则脉冲再快也会被批处理节奏拖住，共振无从谈起。

这个答案决定首步的工作量是 1 周还是 1 个月。
